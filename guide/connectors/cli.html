Connectors CLI

The connectors command is the development CLI for running a personal-local Connector and using its credential-free control surface. Its normal user path is deliberately small:

connectors serve
      ↓ owner-only local socket
connectors connect <provider>
      ↓ one-use, non-echoing credential handoff when needed
Connection → admitted operations, events, and discovered services

The CLI does not accept reusable provider credentials as command-line flags or environment variables. A credential entered through a guided flow does not become a configuration value or JSON output: it travels directly from the terminal to a single-use Connector-owned completion socket. Kubernetes instead uses the selected standard kubeconfig credential source.

Development status

The CLI is a pre-v1 development surface. There is not yet a stable public package or supported installation channel. Use the binary supplied by a Daemonloom development deployment and check connectors --version alongside these docs. Personal-local Slack, Grafana, and Kubernetes flows are implemented development slices; hosted mutation, general OAuth acquisition, and stable SIP exposure are not production-ready capabilities.

Start a personal-local Connector​

The daemon and every client command must use the same configuration and state root. The defaults follow the XDG base directories:

PurposeDefault
Configuration$XDG_CONFIG_HOME/daemonloom/connectors.toml; when XDG is unset, the conventional per-user configuration directory is used
State$XDG_STATE_HOME/daemonloom/connectors, falling back to $HOME/.local/state/daemonloom/connectors
Control socket<state-root>/connectors.sock

An explicit state root must be absolute and outside the current working tree. Keep the configuration owner-controlled; chmod 600 is a suitable default. The file contains policy and opaque authority references, never a provider token.

This minimal Slack Socket Mode configuration is sufficient for the first guided flow:

$XDG_CONFIG_HOME/daemonloom/connectors.toml
[owner]
tenant_id = "tenant-development"
agent_id = "harness-development"
agent_revision = 1
authority_snapshot_id = "snapshot-development-1"
authority_snapshot_sha256 = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"

[slack]
grant_ref = "grant-slack-events-development-1"
initiation = "provider"
allowed_events = ["app_mention", "message.channels"]
connect_session_ttl_seconds = 300

The owner and Grant values above are development placeholders. In a managed deployment they come from the owning authority and policy systems; changing the strings does not manufacture authority.

Start the daemon in one terminal:

CONNECTORS_CONFIG="${XDG_CONFIG_HOME:-$HOME/.config}/daemonloom/connectors.toml"
CONNECTORS_STATE="${XDG_STATE_HOME:-$HOME/.local/state}/daemonloom/connectors"

chmod 600 "$CONNECTORS_CONFIG"
connectors serve --config "$CONNECTORS_CONFIG" --state-root "$CONNECTORS_STATE"

On readiness, the daemon prints a value-free JSON summary and listens on the owner-permissioned Unix socket. Leave it running while using the commands below.

Connect a provider​

connectors connect is the preferred setup path. It hides acquisition plumbing, chooses the correct flow for the provider, and waits for a usable Connection result.

Receive Slack messages​

In a second terminal, use the same configuration and state root:

connectors connect slack \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE"

The CLI prompts for the Slack app token with terminal echo disabled. It does not print or persist the value outside Connector custody. The current guided Slack flow establishes Socket Mode for the configured event vocabulary; it does not perform bot, user, or Enterprise Admin OAuth.

List the resulting Connection and admitted event channel:

connectors connection list \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE"

connectors event search \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE"

Copy the opaque channel_ref from the JSON response, then receive durable normalized events:

connectors event receive \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE" \
  --channel <channel-ref>

The default receive call waits up to 30 seconds and returns at most 25 events. Use --after <cursor> to continue from an opaque cursor, --wait-ms 0 for an immediate poll, or --limit <count> for a smaller bounded batch.

Connect Grafana and its federated data sources​

Add a value-free Grafana section to the personal configuration:

[grafana]
origin = "https://grafana.example"
grant_ref = "grant-grafana-read"
initiation = "daemonloom"
connect_session_ttl_seconds = 300

[grafana.target_grants]
prometheus = "grant-prometheus-read"
loki = "grant-loki-read"
alertmanager = "grant-alertmanager-read"

Restart connectors serve after changing configuration, then run:

connectors connect grafana \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE"

The hidden prompt accepts a Grafana service-account token. The Connector performs its bounded data-source read and materializes only recognized Prometheus, Loki, or Alertmanager targets with an independent configured target Grant. It does not expose data-source UIDs, backend URLs, proxy paths, or the Grafana credential to the CLI.

Inspect observations without materializing additional authority:

connectors connection observations \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE" \
  --source <grafana-connection-ref>

Read Discovery and mediated connections before treating an observation, candidate, Connection, or Grant as interchangeable.

Connect a Kubernetes context​

The Kubernetes flow discovers kubeconfig contexts without asking for a provider token. Add:

[kubernetes]
grant_ref = "grant-kubernetes-local-discovery"
initiation = "daemonloom"
namespaces = ["monitoring"]
allow_exec_auth = false
resource_limit = 256

[kubernetes.target_grants]
grafana = "grant-grafana-cluster-service"
prometheus = "grant-prometheus-cluster-service"
loki = "grant-loki-cluster-service"
alertmanager = "grant-alertmanager-cluster-service"

Restart the daemon, then ask the CLI to enumerate contexts:

connectors connect kubernetes \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE"

If more than one context is present, the command lists their names without contacting their API servers. Select one explicitly:

connectors connect kubernetes \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE" \
  --context <exact-context-name> \
  --label "Development cluster"

Activation performs read-only identity and RBAC checks, then discovers supported monitoring Services within the configured namespace scope. Kubeconfig exec and legacy auth-provider plugins remain disabled unless the operator explicitly sets allow_exec_auth = true; enabling them allows local credential-helper processes to run.

Inspect and invoke operations​

The operation commands emit the typed protocol response as formatted JSON. Search is effective runtime discovery, not the static public catalog:

connectors operation search \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE" \
  --query <text> \
  --limit 25

Before invoking, obtain a fresh description and its opaque lease:

connectors operation describe \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE" \
  --operation <operation-ref>

Then invoke the exact operation and Connection named by that description:

connectors operation invoke \
  --config "$CONNECTORS_CONFIG" \
  --state-root "$CONNECTORS_STATE" \
  --operation <operation-ref> \
  --connection <connection-ref> \
  --description-ref <fresh-description-ref> \
  --input-json '{"field":"value"}' \
  --approval-evidence-ref <approval-ref>

--input-json must be a JSON object containing only catalog-declared caller input. --approval-evidence-ref is optional at the syntax level but an operation or deployment policy can still require approval. A stale description reference, unavailable capability, wrong Connection, missing Grant, or changed authority must refuse rather than silently refresh or fall back.

Catalog presence and the model tool marker do not mean an operation is currently invocable. See Catalog guide and Connections and grants.

Command reference​

Top-level commands​

CommandPurposeIntended user
connectors serve [--config <path>] [--state-root <path>]Run the owner-permissioned personal-local daemon. Without a configuration it starts a refusing protocol skeleton.Developer or local operator
connectors connect <slack|grafana|kubernetes>Run the guided provider-specific Connection flow.Developer or local operator
connectors connection …Inspect or explicitly advance Connection discovery state over the local socket.Operator and diagnostics
connectors operation …Search, describe, or invoke currently admitted operations.Governed client and diagnostics
connectors event …Search channels, receive normalized events, or replay one retained event.Governed client and diagnostics
connectors serve-hosted --config <path>Run the Identity-authenticated hosted API.Deployment operator only

connectors --help, connectors <command> --help, and connectors --version are always the version-matched command reference.

Connection commands​

SubcommandRequired selectionResult
connection candidates--config, --integration; optional --query, --limit, --state-rootPassively lists opaque direct-Connection candidates without provider contact.
connection activate--config, --candidate, --label; optional --state-rootExplicitly contacts and activates one candidate.
connection list--config; optional --query, --limit, --state-rootReturns non-secret Connection summaries.
connection observations--config, --source; optional --query, --limit, --state-rootReturns the latest stored discovery observations for one source Connection.
connection materialize--config, --observation; optional --state-rootMaterializes one recognized observation under its independent configured Grant.

The CLI intentionally hides the lower-level Connect Session creation, polling, and completion commands. Use connectors connect; scripts should not capture or replay a completion endpoint.

Hosted and SIP boundaries​

serve-hosted is a deployment command, not a way for an end user to paste a bearer or provider credential into Connectors. Hosted callers obtain short-lived, exact-audience authority through Identity. The current hosted development service deliberately refuses effect-bearing invocation and Connection mutation until Connector-owned Grant and management admission are complete.

SIP is configured as a deployment-owned development Integration rather than through connectors connect. It requires fixed destination aliases, apertures, independent operation authority, and a separately supervised voice application. Native SIP/RTVBP work remains behind development release gates and should not be presented as stable or generally exposed functionality. Read Beyond HTTP for the protocol boundary.

Security checklist​

  • For the current guided Slack and Grafana flows, enter provider credentials only into the CLI's non-echoing prompt. Kubernetes continues to use its selected kubeconfig credential source.
  • Never add provider tokens, passwords, or ad hoc secret-file indirection to personal configuration. The operator-only SIP authority-key path is a separate deployment trust input, not a provider Connection credential.
  • Keep the configuration and state root owner-controlled and use the same explicit paths for the daemon and client commands.
  • Treat Connection, observation, candidate, channel, event, description, and approval references as opaque. Do not construct them or infer authority from their spelling.
  • Review JSON output before sharing it. It is designed to exclude credentials but can still contain operational metadata such as labels and resource observations.
  • Prefer the guided connect flow. Use lower-level Connection commands only when you understand the lifecycle transition they request.

For the surrounding authority model, continue with Connections and grants, Events and channels, and Operation contracts.
