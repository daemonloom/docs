Evaluate a connector

Finding a provider in the connector explorer is the beginning of evaluation, not the end. The catalog tells you which capability surface has been represented as reviewed canonical data. It does not promise that a deployment, connection, or grant exists for your tenant.

A six-question review​

1. Is the exact operation present?​

Search for the task, then select the stable operation whose description matches the intended effect. Do not infer an undeclared capability from the provider name. Catalog coverage is deliberately narrower than the vendor's complete API.

Check the operation's projection badge separately. Catalog only is still callable through a governed client; it only means the operation is not offered directly to a model by default.

2. Are all effects acceptable?​

Read the full effect set rather than relying on read or write direction alone. A read can still require a network, browser, process, filesystem, or local-system effect. Grants and execution policy need to admit the complete declared set.

3. What consequence and replay behavior are declared?​

Risk informs the configured review path. Idempotency informs what a caller may safely do after a timeout or interrupted response. Neither field grants authority, and neither promises exactly-once delivery.

4. Does the interaction shape fit the workflow?​

A unary request, stream, subscription, leased session, and session establishment have different lifecycle needs. Check required capabilities and placement as separate concerns; transport alone does not tell you where an implementation can run.

5. Are the inputs and outputs sufficient?​

Required inputs show what the invocation must provide. Projected outputs show which response facts the contract makes available to downstream policy and evidence. If a fact you depend on is absent, do not assume the provider response will be forwarded unbounded.

6. How will authority be established?​

Authentication entries describe schemes and subjects, never credential values. Runtime use still requires a served provider, an authorized connection, a matching grant, valid tenant context, and any configured approval.

Worked reading: a visible GitHub write​

The current snapshot's github-issue-comment-add operation demonstrates why these dimensions stay separate:

Contract factWhat it tells the evaluator
Direction: writeThe caller intends to change provider state.
Risk: highThe configured policy should treat the consequence as significant.
Effects: write, networkBoth effects must fit the admitted authority and runtime.
Idempotency: non_idempotentAn uncertain attempt must not be retried blindly.
Interaction: unaryOne request produces one response, though the effect may outlive either.
InputsRepository owner, repository, issue number, and comment body are explicit.
Output URL and IDEvidence can refer to the comment that was actually created.

Its description also states that the comment is visible to repository readers and notifies participants. That consequence is decision-relevant even though it is not a separate protocol field.

What the explorer cannot establish​

Before treating a catalog match as usable, a deployment still needs to answer:

  • Is this provider and operation served here?
  • Is the selected connection valid and healthy?
  • Does the provider-side account have enough permission for this target?
  • Does the requesting principal hold a current grant?
  • Can required placement and capabilities be satisfied?
  • Is the upstream provider available now?

Those are runtime facts. Keeping them out of the static catalog is what lets the explorer remain public and credential-free.

Comparing candidates responsibly​

When several providers can perform similar work, compare the narrowest useful operations, declared effects, retry behavior, interaction shape, required capabilities, authentication subject, model projection status, and projected evidence. Raw operation count is not a quality score.
