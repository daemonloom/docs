Slack connector

Slack is a useful example of why source coverage, callable catalog, and model tools need separate numbers. The current Slack catalog surface traces all 170 operations in Slack's complete public Web API document. Eight are currently reviewed into the callable catalog, alongside two events and two delivery transports. Each selected member names the exact credential purpose and provider scope it requires.

Surface at a glance​

SurfaceCurrent selectionCredential purposeCharacter
Upstream API source170 operations from the complete public Swagger documentvaries upstreamsearchable source inventory; not automatically callable
Web APIpost a message, read public-channel history, inspect a user, add a reactionslack.bot_token or slack.user_tokentwo reads and two writes, attributed to the selected actor
Enterprise Admin APIlist app requests, search conversations, list workspaces, list usersslack.admin_tokenfour read-only organization operations
Eventsapp_mention, message.channelsslack.bot_token plus the event's scopeprovider-originated facts

These are selected, reviewed surfaces—not a promise that every Slack method is present. All eight current operations are eligible for model projection, but that marker does not make them available on a particular Connection.

Four different surfaces​

complete Slack source (170 operations)
    ↓ deterministic selection and review
callable catalog (8 operations)
    ↓ expose = true
model-tool projection (8 operations)
    ↓ current Connection capability + lifecycle + Grant + caller checks
effective runtime surface

The explorer makes the complete 170-operation source inventory searchable so upstream coverage does not disappear behind curation. Source ingestion still grants nothing and selects nothing by default. The callable catalog says which contracts Daemonloom has admitted. Model projection says which of those contracts may enter model context. Runtime admission must narrow the surface again for the selected Connection.

Credential purposes​

The names below are Connector credential purposes. They keep independent provider authorities from being treated as interchangeable strings.

PurposeSubjectUsed for
slack.bot_tokenappselected Web API operations and event subscriptions, attributed to the workspace app bot
slack.user_tokenuserthe same four ordinary Web API operations through principal-owned delegated consent, attributed to that member
slack.admin_tokenuserselected Enterprise organization reads after an org-wide Admin or Owner installation
slack.app_tokenappopening Socket Mode only
slack.signing_secretappverifying Events API webhook signatures only

The bot and user paths can require the same named scope while producing different provider reach and attribution. Slack applies app membership to the bot token and the consenting member's own visibility to the user token. Zwirn remains the Daemonloom caller in either case; the selected Connection decides which actor Slack sees.

slack.admin_token does not describe a new Slack token format. It is a distinct Connector purpose for a user OAuth token established through an Enterprise organization installation with reviewed admin scopes. Likewise, an app-level token does not authorize Web API calls, and a signing secret does not authorize event subscription.

Scope requirements attach to one credential purpose. A runtime must never combine scopes observed on separate credentials to satisfy one member.

Events and transports​

The selected event vocabulary is deliberately closed:

  • app_mention requires app_mentions:read on slack.bot_token;
  • message.channels requires channels:history on slack.bot_token and represents a human message in a public channel the app has joined. Bot and subtype messages are excluded by the channel runtime's loop guard.

Transport authority is separate from event authority. Socket Mode requires slack.app_token with connections:write to open the outbound socket. Events delivered through that socket still need the bot-side subscription scopes above. Events API instead authenticates the inbound HTTP request with slack.signing_secret; it does not need the Socket Mode app token.

See Slack's own descriptions of Socket Mode and the Events API for provider behavior. The Daemonloom catalog remains the authority for which members are selected here.

Credential presence is not operation authority​

A token being present, having a familiar prefix, or having requested scopes is not sufficient proof. The intended runtime model retains value-free capability evidence tied to the current credential generation: credential purpose, provider subject, granted scopes, installation context, evidence source, and freshness.

Discovery and invocation should evaluate the same admission predicate. Missing, stale, or ambiguous evidence removes the member from the effective surface and refuses dispatch. A matching Connector Grant, caller authority, lifecycle state, and implementation availability remain independently required.

The protected connection flow keeps provider secrets inside Connectors. A coding harness or model receives only admitted operations for an opaque Connection; it does not receive Slack credentials.

The app-install and user-consent paths are separate OAuth declarations. Slack expects comma-separated scope requests; the delegated-user token response also reports its granted scope in a provider-specific response field. The host records that result as generic capability evidence rather than teaching a client or model how to parse Slack tokens.

Current implementation boundary​

The catalog tooling now retains Slack's complete 170-operation public Swagger document as source evidence, derives the reviewed Web and Admin selections, and ingests credential-local scope requirements, separate bot-install and delegated-user OAuth acquisition, plus repository-authored AsyncAPI event contracts. The personal-local Socket Mode alpha implements app-token custody, secure connection-ticket minting, event normalization, durable pull, and replay for the selected events.

Generic OAuth acquisition and generation-bound capability evidence for bot, user, and admin Web API operations are still development work. The catalog therefore describes the intended admission contract; it is not a claim that every listed Slack operation is currently invocable in a deployed runtime. Hosted multi-workspace Socket Mode also requires the later Integration-owned transport and workspace Connection split.
