Trace a governed action

Architecture becomes easier to judge when it has to explain one real effect. This walkthrough uses an illustrative request: an agent wants to add a comment to a GitHub issue after detecting a failed deployment check.

The public catalog describes github-issue-comment-add as a high-risk, non-idempotent write with write and network effects. The comment is visible to everyone who can see the repository and can notify participants. Those facts matter before any request reaches GitHub.

Architecture walkthrough

This page traces the intended governed path; it is not a claim that the entire hosted path is available today. Check current status for implementation maturity.

The path at a glance​

versioned intent
  → product admission
  → exact operation + connection + grant
  → configured approval decision
  → external effect
  → correlated observations
  → retry, stop, or improvement proposal

Each arrow crosses a boundary. No earlier “yes” forces the next owner to say yes.

1. Bind the intent​

Before execution, the product binds the proposed work to facts that must remain attributable:

  • the tenant and initiating principal;
  • the immutable agent revision and run;
  • the stable operation ID;
  • the target repository and issue number;
  • the proposed public comment body;
  • applicable budget and evaluation context.

This is more precise than “the agent may use GitHub.” It identifies one requested effect with one set of arguments.

2. Admit the work under product policy​

Product policy answers whether this work makes sense in the customer's context. Because the operation declares high risk and a visible write, a configured decision path may require a human or policy approval before continuing.

That approval is deliberately incomplete. It does not create a Connector grant, prove that the selected GitHub installation can reach the repository, or guarantee that the provider will accept the request.

3. Resolve narrow external authority​

Connectors evaluates the request against its own facts:

  1. Does the requested operation exist in the canonical catalog?
  2. Is it exposed and served by this deployment?
  3. Which authorized connection names the GitHub account or installation?
  4. Does the caller's grant admit the operation's risk and complete effect set?
  5. Does the request satisfy the operation's declared input contract?

Credential requirements are catalog metadata; credential values are not. A usable credential is resolved from the selected connection only inside the governed invocation path.

4. Execute only through the admitted path​

If every required decision succeeds, the selected Connector implementation performs the request. Substrate admission is also required when an implementation needs a separately confined process or workspace. A built-in remote operation does not acquire a Substrate hop merely for symmetry.

The boundary remains fail-closed: an unavailable connection, missing grant, unsupported placement, or required confinement that cannot be established produces a refusal—not a direct-token or host execution fallback.

5. Preserve observations as evidence​

The result should retain enough correlation to answer more than “did it return 201?”

EvidenceQuestion it helps answer
revision and run identifiersWhich behavior produced the request?
principal and tenant bindingFor whom was it acting?
operation and connection referencesWhich external authority path was selected?
decision recordWhich policy or approver admitted the visible write?
request/result correlationWhich provider response belongs to this attempt?
returned comment identity and URLWhat external object was actually created?
timing, usage, and terminal stateWhat did the attempt cost and how did it finish?

These observations retain their provenance. Product evidence may correlate an owner-produced fact; it must not rewrite that fact as if the product observed it directly.

6. Treat uncertainty as a decision​

This operation is non-idempotent. If the network fails after GitHub accepted the comment but before the response arrives, blindly retrying can create a duplicate comment and duplicate notifications.

The correct next step depends on explicit policy and evidence: inspect provider state, request a new decision, stop with an uncertain result, or use an operation-specific recovery strategy. “The request timed out” is not evidence that no effect occurred.

7. Improve by proposing a new revision​

Suppose evaluation shows that the agent comments too eagerly. The learning loop may propose a revision with a stronger evidence threshold or a different approval rule. That candidate is tested and promoted, revised, or rejected through a named gate. The running revision is not silently mutated because one outcome was disappointing.
