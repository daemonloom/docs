Current status

Daemonloom is an early, private development program. The public site describes its intended shape, but working components have different maturity levels and none should be read as a blanket production-readiness claim.

AreaCurrent maturityNext meaningful threshold
Architectureaccepted cross-foundation boundaries and development specificationskeep owner contracts and observed implementation aligned
Agentworkspace 0.4.0; reusable harness/session APIs, terminal and headless projections, pinned Codex and Claude profiles, hosted Identity/Connector catalog client, and separately launched Substrate development conformancepublish and pin owner contract artifacts; add receiver-backed Grant UX, opaque inference credentials, and remote placement only after their authorities exist
Connectors59-provider compiled catalog with 62 verified committed artifacts; development platform families; hosted catalog reads backed by five-minute Identity access authority; personal Slack, Grafana, and Kubernetes development slicesimplement receiver-owned Grant and management admission, durable hosted lifecycle/custody, recovery, and signed owner evidence before enabling hosted mutation
Substratephase 3 lifecycle/recovery plus deterministic 0.4.0 successor development bundle, durable raw-pipe sessions, verified capsules, backend-bound capability snapshots, and bounded Linux executionreplace the development static-bearer TCP overlay with scoped hosted authority; package, sign, and publish owner evidence
AI Agent Platformproduct and boundary designprove the first governed work/evaluation/evidence slice
Guildproduct thesis and dependency-free workforce lifecycle skeletonclose domain invariants and publish a development contract
Identitylocal one-organization OIDC/PKCE bootstrap with opaque sessions, bounded credential state, five-minute Connector access authority, revocation, and SQLite/PostgreSQL storageadd service/deployment trust, key rotation, management/conformance surfaces, distributed database evidence, and a signed owner release
Cloudlocal developer Helm composition with immutable artifacts, private single-writer foundation services, internal Identity/Connectors ingress, and experimental opt-in Vault custodyimplement the deployment descriptor/reconciler and released compatibility, placement, failure, and metering contracts before production claims

Reading status language​

  • Design-stage means a boundary or direction is documented but no conforming service exists.
  • Walking skeleton means a narrow executable path proves domain shape without claiming a full product.
  • Development contract means a versioned interface exists for coordinated development but is not yet a stable owner release.
  • Complete phase refers only to that phase's written exit criteria, not to the whole product.

This page is a rough public summary. Repository-local status documents remain the detailed source of truth while the project is being assembled.
