Know what exists today

The task-fit developer control plane is an accepted product direction with executable development slices underneath it. It is not yet a stable public harness or a production infrastructure and incident operator.

Product pre-v1Work live + controllableDefault bounded

What the current development paths demonstrate​

One engineering run can already demonstrate that it:

  • begins from an explicit objective, workspace, authority reference, and finite limits;
  • streams operator output, tool activity, approval requests, warnings, and usage in order;
  • accepts a correlated approval decision, steering, or cancellation while work is active;
  • keeps repository access read-only unless a broader posture is explicitly selected;
  • mediates a small synthetic external-operation flow without exposing a credential to the worker;
  • ends with completion, failure, or cancellation connected to an attributable event record;
  • carries a model-free development worker through an independently bounded execution environment;

These are executable slices, not screenshots or architecture-only claims. They deliberately test one boundary at a time. A real coding worker against deterministic local inference and a model-free worker inside governed execution are currently separate evidence dimensions; neither implies that the combined path already ran.

What is being built now​

The active direction integrates a reusable core with the existing lifecycle and adapter proofs:

task and passive discovery
  → effective task capability catalog
  → immutable local work profile
  → shared session supervisor
  → terminal UI and headless projections
  → evidence checkpoint

The next integrated walking slice includes passive workspace and Git discovery, one small native read operation, the existing synthetic external-operation provider, one real pinned coding worker, and one denied boundary crossing inside the same governed local session.

Not available yet​

Do not infer any of the following:

  • a stable downloadable public harness or compatibility promise;
  • a hosted or multi-tenant coding service;
  • automatic use of every provider visible in the public Connector catalog;
  • production infrastructure or incident actions using organization credentials;
  • unrestricted network access or sealed secret release inside a coding-worker session;
  • durable organization-wide task storage, scheduling, policy administration, or replay;
  • worker failover, multi-worker orchestration, or direct-model-provider support;
  • a production web console or editor integration;
  • live endpoint discovery, the /discover experience, or an active network probe;
  • an executing Workflow IR, released Work Modes, autonomous proposal board, or personal learning profile;
  • operational readiness for every workflow described in this section.

How to evaluate it responsibly​

The honest current use is product and development evaluation:

  1. use a disposable or deliberately scoped local workspace;
  2. begin with an investigative, read-only task;
  3. provide no production credential or unrestricted service access;
  4. observe whether progress, decisions, controls, and terminal state remain coherent;
  5. record exactly which development path ran and which evidence dimensions did not;
  6. treat infrastructure and incident workflows as the target experience, not a deployment claim.

Next evidence gates​

integrate the reusable engine with passive discovery and one native operation
  → terminal UI and headless parity over that session
  → real coding worker inside the governed local execution closure
  → released read-only Connector binding
  → signed and reproducible distributions
  → controlled destinations and credential release
  → no-effects shadow engineering workflows
  → selected production tasks
