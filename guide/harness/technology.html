Coding harness previewDOC / 06

Technology

The harness is being built as a contract-first Rust system: one deterministic lifecycle, strictly pinned worker adapters, a reusable capability compiler, independent execution and external-operation ports, and evidence that preserves who observed what.

Product pre-v1Work live + controllableDefault bounded

Implementation posture​

Two layers are important when reading this page:

  • implemented development core: lifecycle model, CLI, pinned Codex and Claude adapter edges, synthetic external operations, execution contracts, and model-free governed-execution evidence;
  • accepted architecture in progress: the reusable harness library, provider-neutral capability compiler, Work Modes, collaboration profiles, common session supervisor, minimal terminal UI, and equal headless projection.

Neither layer is a stable production service. Current status remains the public maturity boundary.

They are compatibility identities and implementation bounds, not stability or production-readiness promises. JSON Schema Draft 2020-12 carries the generated contracts; JSONL carries normalized machine events and bounded sidecar or process framing.

Rust owns the generic types, transition machine, process supervision, request validation, profile compilation, Connector-tool bridge, and Substrate adapter. TypeScript exists only where the official Claude SDK requires an owner-language sidecar; Rust launches, bounds, controls, and reaps that process.

Pins are compatibility identities. A binary with another version does not inherit support because its command name or JSON framing looks familiar. SDK version and bundled CLI version are independent facts and both are checked.

Architecture at a glance​

The accepted target keeps every frontend over one reusable engine:

The frontends do not implement separate approval, operation, cancellation, or evidence paths. Changing presentation must not change authority.

Datasource state is a closed progression, not one Boolean:

detected != available != connected != authorized != admitted

The capability compiler consumes passive observations, owner facts, the task, and the product ceiling. It can only narrow their intersection. Unknown states, identifier collisions, stale owner facts, and unsupported effect classes refuse instead of taking registration order or optimistic defaults as authority.

Reusable harness direction​

The architecture extracts orchestration from the CLI into a library-first daemonloom-agent-harness engine. Its initial modules remain together until a real consumer or dependency boundary justifies another crate:

A separate terminal UI and headless frontend are intended to project the same HarnessSession; frontend types and IO remain outside the reusable library.

Work Modes and collaboration profile​

The product design keeps five choices independent: work mode, activity posture, worker, model or inference route, and reasoning effort. A public Work Mode is intended to bind a digest-pinned typed workflow graph, capability ceiling, approval and effect posture, limits, evaluation, and visible widgets. autonomous and prompt describe who normally initiates work; neither changes authority.

The Workflow IR, Work Mode validation, proposal board, and personal collaboration profile are active development work. They are not a released workflow executor or learning system.

Lifecycle contract​

The current core transition is deliberately small:

pending → running ⇄ awaiting-approval → completed
              │              │
              ├──────────────┴→ cancelling → cancelled
              └────────────────────────────→ failed

Every normalized event carries a run id and a strictly increasing run-local sequence. The closed event vocabulary covers start, output delta, tool request/completion, approval request/resolution, delegation, usage, warning, cancellation request, and one terminal result.

Controls are equally small: resolve approval, steer, and cancel. A control unsupported by the active state or adapter is a typed refusal and never reaches the child process. A cancellation request wins over a late completion until the owning execution path reconciles terminal state.

Run request​

A strict request binds one engineering task to an immutable revision and operating context:

{
  "run_id": "engineering-run-42",
  "agent": {
    "tenant_id": "local-tenant",
    "agent_id": "repository-engineer",
    "revision": 1,
    "behavior": {
      "media_type": "text/plain",
      "format_version": "v1",
      "sha256": "digest-of-the-exact-behavior-body",
      "body": "Follow the task safely."
    },
    "instructions": "Investigate the failure and return concise evidence.",
    "capabilities": ["harness.codex.command-execution"],
    "delegates": [],
    "driver": {
      "class": "harness",
      "adapter_id": "codex-app-server",
      "capabilities": ["streaming-output", "tool-calls", "approval-suspension", "cancellation"]
    }
  },
  "initiator": {"kind": "tenant-member", "principal_id": "local-operator"},
  "authority": {"id": "authority-snapshot", "sha256": "authority-digest"},
  "channel": {"kind": "cli", "session_id": "terminal-session"},
  "input": {"kind": "text", "value": "Find why the deployment test fails; make no changes."},
  "constraints": {
    "admission_timeout_ms": 5000,
    "startup_timeout_ms": 30000,
    "run_timeout_ms": 300000,
    "approval_timeout_ms": 300000,
    "cancellation_timeout_ms": 5000
  }
}

The current CLI accepts at most 1 MiB, rejects unknown fields, verifies the behavior digest, and supports only text input with text/plain behavior format v1. Unsupported structured input is refused rather than stringified.

Current command and process boundary​

The current explicit development surface is:

agent-harness inspect --adapter codex
agent-harness conformance --adapter codex
agent-harness probe --adapter codex
agent-harness run --adapter codex \
  --request request.json \
  --cwd /absolute/path/to/workspace \
  --sandbox read-only

inspect verifies installed identity. conformance runs a bundled offline trace. probe performs only initialization and bounded shutdown; it starts no thread, turn, or model. run is explicitly model-backed and defaults to read-only; writable workspace access requires --sandbox workspace-write.

Stdout is normalized RunEvent JSONL. Diagnostics and human approval prompts stay on stderr; interactive decisions use stdin. Ctrl-C requests correlated cancellation and waits for a terminal acknowledgement before the child reaches its termination bound.

The accepted default interface is a minimal TUI over the reusable engine, with an equal headless mode. That default has not replaced the current CLI yet.

Worker profiles​

Codex uses a closed stdio app-server subset: initialization, thread start/resume, turn start/steer/ interrupt, streamed items, command and file approvals, warnings, usage, and terminal status. A governed preflight additionally verifies effective configuration, requirements, and native hooks.

Claude uses a distinct owned Node sidecar. Rust replaces its environment, supplies only reviewed values, maps revision grants to selected SDK tools, replays sidecar events through the same run machine, and owns cancellation and process reap. Claude JSONL is never treated as Codex compatibility.

A future direct-provider adapter is a separate class. Its model connection must remain Connector-managed, and failure never falls back to harness login or another billing identity.

Operation surface​

The current experimental Codex proof exposes three Connector-specific functions:

daemonloom_connector_search
daemonloom_connector_describe
daemonloom_connector_invoke

The outer supervisor validates tool, run, turn, and call correlation; applies input and output bounds; calls a credential-free port; and returns bounded text. The worker cannot select a daemon URL, executable, credential, tenant, endpoint, or approval evidence. Search is not a grant, describe does not reserve authority, and invoke re-evaluates the operation.

That binding is synthetic. The accepted reusable design adds a separately identified, provider-neutral search/describe/invoke profile where harness-native and Connector-backed providers are peers in one effective catalog. It does not silently change the meaning of the already pinned Connector-specific evidence.

Governed execution​

Agent compiles the runtime, effective configuration, protocol sidecars, and native hook handlers into one digest-addressed execution profile and immutable capsule. Mutable tenant work remains on a separate workspace mount. Dispatch requires Substrate to report the expected capsule identity and read-only runtime posture.

The current delegated path proves this with a model-free fake worker under an empty initial environment, no egress, bounded protocol pipes, independent process-tree termination, and durable terminal reconciliation. Real pinned Codex against deterministic inference passes separately on a direct-host development path. Combining those paths into one governed closure is a named next gate.

Evidence dimensions​

Conformance is never one Boolean:

DimensionWhat it establishes
portable_lifecyclegeneric state-machine behavior from executable vectors
profile_fixturepinned adapter protocol projection
processowned child process and bounded framing behavior
provider_emulatedreal harness against deterministic local inference
connector_syntheticcredential-free external-operation callback shape
substrate_confinedindependently observed governed execution path
vendor_liveexplicitly authorized live-vendor characterization; not currently claimed

Receipts retain agent-normalized, harness-reported, hook-reported, connector-audited, and substrate-observed provenance. Reconciliation concludes complete, contradictory, missing required evidence, or outcome unknown. It contains no aggregate safe field.

Development methodology​

Contract first​

Typed Rust definitions generate strict JSON Schemas and portable lifecycle vectors. Generated bytes are read back, meta-schema checked, decoded, and executed. Committed contract artifacts are never hand-edited.

Positive and adversarial evidence​

Every advertised behavior needs executable evidence. Tests cover happy paths alongside version drift, missing capabilities, unknown messages, stale correlation, duplicate approval, output flood, quiet-child cancellation, protocol loss, descendant survival, endpoint drift, retry bounds, credential leakage, and forbidden fallback.

Clean-room owner boundaries​

Cross-repository integration consumes copied or released contract bytes, never sibling source or path dependencies. An independent standard-library consumer executes the lifecycle vectors without sharing the Rust implementation.

Pure core, effects at ports​

The lifecycle transition is deterministic. Persistence, clocks, worker IO, external operations, and execution are injected ports. Vendor DTOs stop at adapter crates; terminal and frontend types stop at their projections.

Evidence dimensions stay separate​

Protocol, process, local inference, synthetic Connector, confinement, and live-vendor evidence are reported independently. One passing lane never implies an owner boundary that did not run.

Exact dependencies and reproducible gates​

Rust uses the locked workspace. The TypeScript sidecar uses an exact lockfile and checked runtime packlist. Formatting, linting, tests, contract regeneration, boundary checks, profile-hash checks, release consistency, and the independent consumer gate every change.
