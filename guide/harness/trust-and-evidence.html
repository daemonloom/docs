Useful autonomy needs visible boundaries

The engineer experiences one coherent work loop. Underneath it, discovery, authority, credentials, execution, approvals, and evidence remain separate so no convenient shortcut becomes ambient power.

Product pre-v1Work live + controllableDefault bounded

The boundary is compiled for the task​

The harness combines the task, passive environment observations, owner-issued authority facts, and product policy into one effective working boundary. That compilation may narrow what is available; it cannot manufacture a permission that no owner granted.

task + observed environment + owner facts + policy ceiling
                              │
                              ▼
                   effective work boundary
          workspace + operations + worker + limits + evidence

The result is immutable for the admitted work. If a useful next step needs more access or a different consequence, the harness proposes a new boundary rather than editing history in place.

Discovery is not authority​

A datasource is any context a worker may reason over: a workspace, Git repository, CI system, issue tracker, log source, cluster, database, artifact store, documentation corpus, or remote execution environment.

Its states remain distinct: detected, available, connected, authorized, and admitted are separate facts rather than one optimistic Boolean.

StateMeaning
DetectedA bounded observation suggests the source exists.
AvailableThe relevant provider or local capability can be served here.
ConnectedA valid owner-managed connection exists.
AuthorizedCurrent owner facts allow the principal to request applicable operations.
AdmittedThis exact task may use the selected source and operation under its current policy.

Seeing a Git remote or cluster context does not make it usable. Searching an operation catalog is not a grant. Describing an operation does not reserve authority. Invocation re-evaluates the decision at the effect boundary.

Endpoints and Grants stay explicit​

A boundary says where work may occur; an endpoint identifies one concrete remote system inside that boundary. Passive discovery may report an endpoint without probing it. An optional active probe needs a separate, short-lived discovery Grant and still creates no operating authority.

Selecting an endpoint produces a scoped endpoint Grant with a subject, generation, maximum effect, and owner evidence. The reusable design requires that active Grant before it surfaces a Connector-backed datasource. Revocation creates a durable higher-generation tombstone and removes the endpoint's operations on recompile. Rediscovery cannot reinterpret revocation as consent.

One experience, several owners​

The coding harness is the live work surface, but it is not the source of every truth it presents.

OwnerProtectsWhat the work loop receives
Productobjective, workflow policy, evaluation, deliveryone admitted engineering task
Agentrevision, lifecycle, controls, event orderingone controllable run
Coding workermodel loop, native session, supported tool behavioronly the selected profile and capabilities
Connectorsexternal operations, grants, credentials, redaction, auditschemas, opaque references, bounded results
Substrateworkspace, runtime, process tree, resourcesadmitted execution and independent observations

These boundaries prevent a useful coding worker from becoming a universal authority simply because it can reason about many systems.

Credentials stay outside the worker​

Harness authentication remains with the selected harness. External-system credentials remain with Connectors. Neither credential class belongs in the task, prompt, transcript, generic environment, fixture, or evidence packet.

When external context is needed, the worker searches and describes the effective operation catalog, then requests one invocation through the supervisor. The worker cannot select a daemon URL, credential, tenant, executable, raw endpoint, or evidence of its own approval. Only a bounded, redacted result returns to the work loop.

Approval is a boundary decision​

An approval belongs to one active proposal. It identifies the target, requested change, deciding principal or policy, current boundary, and validity period. It cannot be manufactured from model text, applied to a different request, or reused after the relevant facts changed.

Approval means “this exact action may proceed.” It does not mean the action succeeded, that every future action of the same type is allowed, or that the worker is now generally trusted.

This is also how the design avoids permission fatigue: routine work inside the admitted boundary is fluid; only a meaningful authority delta returns to the engineer.

Failure never widens the path​

If a required operation, worker profile, execution boundary, authority fact, or evidence path is unavailable, the run refuses or fails with that fact intact. It does not retry through raw HTTP, ambient shell credentials, direct host execution, another worker, or a different provider account.

Trying a materially different path requires a new task decision. That makes recovery slower than a hidden shortcut in the moment—and far easier to explain during review or an incident.

Evidence keeps its provenance​

The final record correlates facts without pretending one system observed everything:

Evidence sourceWhat it can support
Agentrun ordering, controls, active work, and terminal lifecycle
Coding workernative session and worker-reported activity
Connectorsadmitted external operation, redaction, and provider-facing audit
Substrateprocess, runtime, workspace, resource, and termination observations
Product and engineerwhether the evidence satisfies the engineering objective

Those facts may agree, contradict one another, or remain incomplete. There is deliberately no single “safe” or “successful” switch that erases those distinctions.

Cancellation, recovery, and uncertainty​

A completed, failed, or cancelled run is terminal. A cancellation request waits for terminal acknowledgement. An external provider may have accepted an effect just before a response was lost; a worker process may have stopped while a descendant remains unproven. In either case, the correct state is outcome unknown until the owning boundary reconciles it.

Recovery creates new attributable work: inspect provider state, compensate, retry under an idempotency rule, restore a checkpoint, or begin a replacement task. It does not edit the earlier attempt until it appears successful.

Review a proposed session​

Before admitting work, ask:

  1. Is the outcome precise enough to know when to stop?
  2. Which detected sources are actually admitted, and why?
  3. Which effects can occur without another decision?
  4. Where do credentials and model authentication remain?
  5. What happens if the worker, Connector, or execution boundary fails?
  6. Which independent observations are required for completion?
  7. Can the result be inspected, handed off, or reversed without trusting the transcript alone?
