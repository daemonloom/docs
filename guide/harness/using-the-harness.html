Work with the harness

Describe an outcome, review the proposed boundary, then let the worker move fluidly inside it. You remain in control of boundary changes and decide whether the final evidence is enough.

Product pre-v1Work live + controllableDefault bounded

1. Write the work packet​

Describe the desired outcome rather than prescribing an unbounded command sequence. Include the facts already known, relevant workspace or environment, allowed changes, hard exclusions, and what would make the result credible.

Outcome:      Explain why release 42 fails before rollout.
Scope:        Repository and CI pipeline for release 42.
Start mode:   Read only; do not retry, push, deploy, or change configuration.
Known facts:  Build passes. Deployment validation fails after revision abc123.
Stop when:    The cause is evidenced, access is insufficient, or a mutation is needed.
Done means:   A source-linked explanation, ruled-out hypotheses, and the safest next action.

Do not place passwords, API keys, private keys, or reusable bearer tokens in the work packet. A task names approved sources and operations; credential custody stays outside the coding loop.

2. Review the proposed boundary​

Before work begins, the harness should present a compact preflight:

Preflight factWhat to check
OutcomeIs this still the problem you intend to solve?
WorkspaceIs access read-only or writable, and to exactly which tree?
SourcesWhich repositories, CI systems, logs, clusters, or documents were detected?
OperationsWhich actions are admitted, unavailable, or approval-gated?
WorkerWhich coding worker and profile will own this session?
NetworkWhich destinations, if any, can be reached?
BoundsWhat time, resource, turn, and cost ceilings apply?
CompletionWhich checks and observations are required?

Detection is informational. The preflight must distinguish a source that was merely found from one that is connected, authorized, and admitted to the task.

3. Admit once, work fluidly​

Maximum safety should not mean a confirmation dialog before every read, edit, or test. Once the task-fit boundary is admitted, the worker can explore and iterate inside it without asking again for authority it already has.

Examples of ordinary in-boundary work include reading admitted files, making changes inside the selected worktree, running allowed checks, and using admitted read operations. Examples of boundary changes include widening workspace access, opening a new network destination, spending beyond the current ceiling, pushing, merging, deploying, or invoking a mutating external operation.

4. Follow the work live​

The session exposes operator-facing output and structured activity while work is active:

  • progress and assistant output;
  • requested and completed workspace or external operations;
  • approval requests and their resolution;
  • warnings, limits, and known or unknown usage;
  • steering and cancellation state;
  • the final completed, failed, or cancelled result.

The important view is not a raw process transcript. It is a project-style record that keeps the objective, current work, operations, decisions, budget, and evidence connected.

5. Intervene deliberately​

Steer when new information changes the best next step but not the admitted boundary. A useful steer adds a fact, corrects an assumption, changes priority, or asks the worker to stop pursuing one hypothesis.

Approve or deny one proposed boundary change or consequential action. The decision should show the exact authority delta: target, arguments or safe summary, effect, risk, connection or placement, expiry, and what happens if no decision arrives.

Cancel when the task is no longer useful, the risk posture changed, or time and cost limits are exhausted. “Cancellation requested” is not yet “work stopped”; terminal acknowledgement and execution evidence close that loop.

Switching worker, model path, workspace, authority scope, or effect class is not steering. It needs a new admitted profile or run so the earlier record remains truthful.

6. Decide whether the work is complete​

The harness can report what happened. The product and engineer decide whether that satisfies the engineering goal.

A useful completion packet can include:

EvidenceExample
Resultexplanation, recommendation, patch, or mitigation summary
Workspacediff, commits, changed files, generated artifacts
Verificationtests, builds, static checks, queries, health observations
External workadmitted operation, approval, audit reference, observed effect
Limitselapsed time, known usage, exhausted or remaining bounds
Uncertaintymissing access, warnings, contradictory facts, outcome-unknown effects
Checkpointreversible worktree, artifact, or handoff state for the next decision

“The worker said it succeeded” is not verification. A green test does not prove deployment. An approval does not prove an external effect. Keep each claim attached to the evidence source that can actually support it.

Example: a failing deployment​

An engineer submits the work packet above. The harness proposes read-only repository and CI access, no production connection, a finite run budget, and a completion rule requiring the failure to be correlated with source or job evidence. The worker traces the release revision, inspects the failed job, and rules out two hypotheses.

It determines that a configuration revision is the likely cause. Retrying the deployment would cross the current boundary, so the session presents that action separately instead of doing it. The engineer can stop with an evidence-backed diagnosis, steer toward another hypothesis, or admit a new task for the operational change.
