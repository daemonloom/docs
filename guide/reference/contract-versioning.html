Contract versioning

Daemonloom components coordinate through owner-issued contracts: schemas, canonical catalog documents, lifecycle rules, and development bundles. A version identifies bytes and semantics; it is not a marketing label for an entire project.

Compatibility dimensions​

ChangeReview question
Additive fieldCan older consumers ignore it safely? Is absence meaningful?
New enum valueDo consumers fail closed or misclassify an unknown value?
Stricter validationWhich previously accepted messages will now be refused?
Lifecycle changeCan old and new participants agree on ordering and terminal behavior?
Catalog changeDoes it widen effects, authority, risk, inputs, outputs, or placement?
Removal or renameWhat migration and overlap window preserves attribution?

Schema compatibility alone is not enough when meaning changes.

Canonical artifacts​

Generated owner artifacts let consumers review and pin exact output rather than rebuilding meaning from mutable source at runtime. A digest can establish byte identity; the owner contract explains what those bytes mean.

Unknown values fail deliberately​

Security- and lifecycle-relevant closed vocabularies should not silently map unknown values to a permissive default. A consumer either supports the version and value or returns a typed refusal.

Development versus stable releases​

A development contract supports coordinated implementation but may still change before a stable owner release. Public maturity language should name that difference. A completed internal phase is not automatically a stable cross-project promise.

Migration evidence​

A rollout records which producer and consumer versions were tested, what compatibility window applies, and how rollback works. Runs and external effects retain the contract references that were valid when they occurred.
