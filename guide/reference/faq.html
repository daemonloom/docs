Frequently asked questions

Is Daemonloom a single agent framework?​

No. It is a family of focused systems. Agent owns the generic run lifecycle; Connectors owns external capability authority; Substrate owns bounded execution; products own customer purpose and policy. The system map shows the dependency direction.

Can I deploy the complete platform today?​

Not as a production-ready whole. Daemonloom is pre-v1, and its components have different maturity levels ranging from accepted design to development implementations. Read current status before interpreting any capability description as a release claim.

What is the coding harness?​

It is Daemonloom's local-first developer control plane for software, infrastructure, incident, and complex engineering work. It begins with a desired outcome and shapes a task-fit workspace, source set, operations, worker, limits, approval boundary, and evidence plan around it. Start with the Coding harness; check its current status before treating the product direction as available software.

Does detecting a repository, cluster, or datasource grant access?​

No. Detected, available, connected, authorized, and admitted are distinct states. Passive discovery can help propose a useful task boundary, but only owner-issued authority and task admission make an operation available to the worker.

Can the harness silently switch coding workers after a failure?​

No. Worker identity is part of the admitted run. Changing from one harness or model path to another creates a newly attributable decision with its own compatibility, credential, cost, and evidence facts.

Does the connector catalog mean every connector is live?​

No. Catalog presence means a capability is represented as reviewable canonical data and passes catalog structure gates. Runtime use still depends on a deployment serving it, an authorized connection, a matching grant, and provider availability. See Evaluate a connector.

Does the public catalog contain credentials?​

No. It describes authentication requirements such as schemes and subjects. Credential values are resolved from an authorized connection only inside the runtime boundary and are never part of the public snapshot.

Is a product approval enough to call an external API?​

No. Product policy, Connector authority, and required execution admission are independent gates. One system's affirmative decision does not manufacture another system's authority.

Does a failed control fall back to a weaker execution path?​

No. A governed path refuses when required authority, capability, placement, or confinement cannot be established. Direct credentials, ambient host execution, and stale authority are not recovery paths.

What does self-improvement mean here?​

Observed outcomes can produce a candidate behavior revision. The candidate is evaluated and then promoted, revised, rejected, or rolled back through attributable policy. It does not silently alter the live revision.

Does every connector action run in Substrate?​

No. Substrate is required when the selected implementation needs bounded process or workspace execution. A built-in remote Connector operation can stay in the Connectors deployment. Placement and interaction protocol are separate contract facts.

Where should I start?​

Use Choose a path for a role-based route. For a concrete example, Trace a governed action follows one visible write from intent through evidence and retry handling.
