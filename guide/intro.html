Systems for governed autonomy

Daemonloom is a family of focused systems for building agents that can perform useful work, interact with real organizations, and improve over time while remaining bounded and accountable.

It begins with a simple premise: greater capability should not require less legibility.

An agent action should retain a chain of custody. We should be able to establish which version acted, for whom, under which grant, inside which execution boundary, with which approvals, at what cost, and with what observed result.

Early foundation

Daemonloom is pre-v1. Several repositories contain working contracts and walking skeletons, while other layers remain accepted architecture or planned work. These docs deliberately separate the vision from what exists today.

The idea in one loop​

define → evaluate → authorize → run → observe → propose improvement
  ▲                                                        │
  └──── promote, reject, revise, or roll back ◀──── gate ──┘

Agent behavior is versioned. Capabilities are granted rather than ambient. Execution is bounded. Outcomes become evidence. Learning produces a candidate revision, not an invisible mutation to the live agent.

What Daemonloom is​

Daemonloom is deliberately split into independently meaningful domains:

  • Agent owns the generic run lifecycle: tools, approvals, delegation, events, steering, and cancellation.
  • Connectors owns access to external systems: credentials, grants, invocation, and delivery.
  • Substrate owns bounded execution: confined workspaces, processes, resources, and observations.
  • Identity owns principals, organizations, membership, login, and sessions; its current implementation is a bounded one-organization developer bootstrap.
  • Cloud owns deployment composition without acquiring domain policy; its current Helm profile is a developer composition, not a production control plane.
  • Products such as the AI Agent Platform and Guild give these primitives customer-facing purpose, policy, and experience.

The dependency direction matters. Products may compose the foundation; the foundation must never learn product-specific roles or policy.
