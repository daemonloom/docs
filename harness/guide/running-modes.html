Choose where Zwirn and Connectors run

One Zwirn application supports local and deployed use. Application placement, Identity authentication, and Connector placement are independent choices; Harness execution is a separate boundary again. The effective mode must be explicit, and an unavailable route refuses instead of silently selecting another Connector.

Development contract

The table below describes the intended operating model, not four released products. The local development surface exists today. Cloud-authenticated local operation and the complete deployed experience are still being integrated, and the current status remains the maturity boundary.

The four operating modes​

ModeApplication placementIdentityConnector routesIntended experience
A — local onlylocalno cloud loginlocal Connector daemon onlyrun the full local application against deliberately selected local Connections
B — local hybridlocalcloud authenticatedlocal and remote Connectorsuse local Connections and account-scoped remote Connections in the same application
C — local, cloud Connectorslocalcloud authenticatedremote Connectors onlykeep the application on the workstation while every selected external operation crosses the authenticated remote Connector boundary
D — fully deployeddeployedcloud login mandatoryremote Connectors onlyopen the deployed application, sign in, and use the same full web workspace and Harness against remote Connections

“Local without login” means without a cloud account session. It does not mean an unauthenticated public web server. The local browser surface binds to loopback and requires its unguessable local session capability. That capability is local access control; it is not an Identity login and must not be shared.

Mode D login contract​

The fully deployed mode has one deliberate entry flow:

open the deployed application
  → no valid Identity session: show the landing page and login action only
  → complete OAuth login
  → return with a secure server-side session
  → valid Identity session: open the full web workspace and Harness

Without a valid session, the deployed server must refuse application APIs, Harness interaction, and session WebSocket establishment. A successful login returns to the same application; it must not lead to a reduced hosted shell or a documentation page. Mode D is the target contract while the authenticated full-workspace deployment is being completed and verified.

Placement is a set of independent decisions​

Do not encode the four rows as unrelated product variants. Resolve these dimensions explicitly:

DimensionChoicesBoundary it controls
Application placementlocal or deployedwhere the application and browser-session owner run
Identity postureno cloud login or cloud authenticatedwhether account-scoped remote authority may be requested; deployed placement requires it
Connector placementlocal, remote, or bothwhich Connector owners may surface and invoke selected Endpoints
Harness executionlocal or an explicitly admitted remote execution routewhere worker execution occurs; this is not implied by Connector placement

Connector routing is always explicit. When local and remote routes coexist, their Connections and Endpoints remain separately identified. If a selected Connector is unavailable, the application refuses that operation; it does not fall back to another daemon, account, route, or credential source.

Secrets remain Connector-owned​

The application, the Harness, the worker, prompts, browser storage, and session cookies are not credential stores. A remote Connection's reusable provider secrets remain in the remote Connectors SecretStore. A local Connection's secrets remain in the local Connector's approved store. The application receives value-free Endpoint metadata, admitted operation descriptions, and bounded results—not provider tokens or a generic authenticated proxy.

Signing into Identity establishes the user's application session. It may support short-lived, audience-bound authority for remote Connector operations, but it does not turn the Identity session or browser into storage for Slack tokens, API keys, or other provider credentials.

What this means for Harness execution​

Connector placement answers who owns an external operation. It does not decide where the coding worker, workspace, or governed execution environment runs. For example, a locally running application may use remote Connectors while the Harness remains local. Conversely, a future admitted remote execution route still receives only the effective operation surface; it does not gain Connector credentials or direct provider access.

Use Connecting services for the currently implemented selection paths, then check Current status before treating any mode as available end to end.
