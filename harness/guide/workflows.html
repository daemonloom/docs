Shape the work, not just the prompt

The same harness can investigate a repository, change software, inspect infrastructure, or support an incident. The useful difference is the task boundary and the evidence needed at the end.

Product pre-v1Work live + controllableDefault bounded

Choose a work mode​

Begin with the least consequential mode that can answer the question.

Here, the names are user-facing task recipes. In the product design, a Work Mode is more exact: a versioned binding of workflow, activity posture, worker and model defaults, capability ceiling, approval rules, budgets, evaluation, and visible controls. That executor is not released today.

Work modeStarting boundaryTypical result
Understandread-only workspace and sourcesfindings tied to source evidence
Changebounded writable workspacereviewed diff, checks, and remaining risks
Operateselected external operationsaudited action and observed outcome
Respondtime-bounded investigation with gated mutationstimeline, mitigation, verification, handoff
Decideread-heavy cross-system analysisoptions, tradeoffs, recommendation, open questions

A task can move from one mode to another, but the transition is visible. “Understand why the deployment failed” does not silently become “retry production.” A changed effect, authority scope, workspace posture, worker, or budget needs a newly admitted boundary.

Software engineering​

Software work should preserve the distinction between understanding, changing, verifying, and delivering.

Good tasks include:

  • map an unfamiliar repository before proposing a change;
  • trace a defect from symptom through tests and implementation;
  • implement a bounded feature or refactor against explicit acceptance criteria;
  • migrate a contract without silently widening compatibility;
  • investigate a failing build, test, lint, or release gate;
  • review a risky patch against repository rules and architecture.

The working set can include the repository, one isolated worktree, local build and test tools, and selected read-only development sources. A useful completion record names changed files and artifacts, checks that ran, warnings, known omissions, and whether any push, merge, release, or deployment occurred. Delivery is a separate consequence, not the automatic end of coding.

Infrastructure investigation​

Infrastructure work needs correlated system context, not ambient shell access. The task may admit specific read operations over CI, logs, metrics, workloads, configuration, or cloud state while leaving mutations unavailable.

Use it to:

  • compare intended and observed deployment state;
  • inspect a pipeline, job, workload, or service signal;
  • correlate configuration revisions with logs and health evidence;
  • prepare a bounded operational change for review;
  • verify whether an approved action reached the expected result.

External operations travel through the governed Connector boundary. The coding worker receives descriptions, opaque references, and bounded results—not the datasource credential or a raw service endpoint. If the admitted operation is absent, the run reports the gap instead of improvising a credential-bearing HTTP or shell fallback.

Incident response​

During an incident, the harness should reduce cognitive load without becoming an unaccountable autopilot.

observe → form a hypothesis → test safely → mitigate with approval → verify → hand off

A strong incident task includes:

  1. the current symptom, severity, and affected scope;
  2. known facts separated from hypotheses;
  3. admitted systems and diagnostic operations;
  4. every mutation that requires human or policy approval;
  5. time, budget, cancellation, escalation, and handoff conditions;
  6. the evidence needed to declare mitigation or recovery.

The live work record can become part of the incident timeline. Steering incorporates new facts without erasing earlier reasoning. Approval permits one correlated action; it does not claim that the action worked. Recovery needs a separately observed outcome.

Complex and cross-system problems​

Some engineering tasks begin without a known fix: performance regressions, architecture choices, migrations, security findings, operational debt, or failures spanning several owners.

Use the harness to make uncertainty tractable:

  • inventory relevant repositories, services, documents, and missing access;
  • record assumptions separately from observations;
  • decompose the problem while keeping the original outcome visible;
  • compare options against explicit constraints and acceptance criteria;
  • pause when the next step needs a new source, effect, worker, budget, or authority decision;
  • finish with a recommendation, implemented change, experiment, or bounded unresolved question.

For this work, “done” may be a well-supported decision rather than a code change. The evidence contract should say which one is expected.

Worker choice follows the task​

Selecting a coding worker changes the model loop and native capabilities. It does not change the workspace, datasource authority, approval posture, or evidence requirements. A failed worker does not silently become a different worker or billing path; trying another is a newly attributable decision.

The longer-term direction allows one or more workers to operate under explicit ownership inside the same task boundary. That is product direction, not a claim that multi-worker orchestration is available today.

Know when to reframe​

Stop and create a new boundary when:

  • the desired outcome materially changes;
  • read-only work needs to become writable or operational;
  • a new repository, environment, datasource, or network destination is required;
  • the worker, model path, time limit, or cost ceiling changes;
  • the proposed effect is not covered by the current approval posture;
  • existing evidence is insufficient to determine whether an earlier effect happened.

Continue with using the harness for the session flow. Not every target workflow is operational today; current status is the maturity boundary.
