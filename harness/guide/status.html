Where Zwirn stands today

Zwirn is a source-installable pre-v1 development build with a real TUI, loopback web workspace, JSONL frontend, pinned Codex route, native workspace-status operation, and explicit Connector Endpoint selection. It is not a general coding workspace, stable distribution, hosted service, or production operator yet.

Do not combine those rows into “the whole product ran governed with real provider and production credentials.” Each path proves different facts.

Implemented controls worth evaluating​

  • passive workspace/Git/worker observations remain distinct from owner admission;
  • exact profile generations/digests reject stale catalog or approval state;
  • /surface workspace.status off narrows immediately and restoration needs the exact reviewed delta;
  • a worker/provider refusal never selects HTTP, shell, another worker, or another inference route;
  • repeated prompts retain the Codex conversation but receive fresh governed operation sessions;
  • cancellation cannot later become successful completion;
  • Agent, worker, Connector, and Substrate evidence remain separately attributed.

Still unavailable​

  • general project file tools, writable worktrees, tests, terminal, diff, and preview;
  • a released Work Mode catalog for Understand/Change/Operate/Respond/Decide recipes;
  • active Endpoint selection and revocation inside the TUI itself;
  • general hosted Connector invocation or production infrastructure/incident changes;
  • unrestricted network, secret release into the worker, or direct-provider adapters;
  • durable reconnect/replay, remote browser sessions, scheduling, parallel agents, and cloud placement;
  • datasource search/list/get, compact projections, and Workflow input/output modifiers.

How to evaluate it responsibly​

The honest current use is product and development evaluation:

  1. use a disposable or deliberately scoped local workspace;
  2. begin with an investigative, read-only task;
  3. provide no production credential or unrestricted service access;
  4. observe whether progress, decisions, controls, and terminal state remain coherent;
  5. record exactly which development path ran and which evidence dimensions did not;
  6. treat infrastructure and incident workflows as the target experience, not a deployment claim.
