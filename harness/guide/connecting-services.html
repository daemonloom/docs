Connect an Endpoint to Zwirn

An operator selects a Connector-owned Connection. Agent receives a value-free Endpoint projection and the operations admitted for the run. The worker receives operation descriptions and an opaque target—not the Connection, credential, provider URL, or route.

Product pre-v1Work controllable dev coreDefault bounded
Current development boundary

Two explicit selection paths exist: local Kubernetes Service discovery/materialization and an Identity-authenticated hosted Connection catalog. Local supported reads can be projected into the next session. Hosted selection also projects an Endpoint, but hosted invocation remains receiver-refused until Connector-owned Grant admission ships. This is not a released general Connector binding.

Select a local Kubernetes service​

First list contexts without contacting a cluster:

zwirn connect kubernetes

Expected shape:

Kubernetes contexts (no cluster contacted):
  dev-cluster
Select one with `zwirn connect kubernetes --context <exact-name>`.

Activate one exact context to discover supported Services, then select one exact namespace/name:

zwirn connect kubernetes --context dev-cluster
zwirn connect kubernetes \
  --context dev-cluster \
  --service monitoring/prometheus

The last step stores the Connector config/socket paths and opaque Connection reference in the owner-only Zwirn selection file. It does not copy kubeconfig, an auth-helper result, provider credential, backend URL, or proxy route into Zwirn. Start a new session and inspect /endpoints or /tools to see what the current owner facts actually surface.

Use --json for the same bounded stages in scripts. --connectors-config and --connectors-socket select explicit local owner inputs.

Select a hosted catalog Connection​

Sign in, list callable catalog entries, then select one exact label or opaque reference:

zwirn login identity.daemonloom.example
zwirn connect hosted
zwirn connect hosted \
  --connection "Development cluster (read-only)"

Zwirn stores only the HTTPS API base, an opaque digest binding the selection to the signed-in account, and Connection refs. On startup it requires the same non-expired account and requests a five-minute catalog-read token. The native keyring session is not sent to Connectors or JavaScript.

The resulting Endpoint and operation descriptions can appear in the session, but invocation still refuses today because the hosted receiver has no admitted Connector Grant. Repeating login, rewriting the prompt, or approving inside Agent cannot create that owner authority.

Inspect or remove selections​

Inside the TUI, use /endpoints, /tools, and /profile to inspect the compiled session surface. To remove every persisted local and hosted Zwirn selection:

zwirn connect reset

The reset is monotonic at the Agent selection boundary. It leaves Connector-owned Connections, credentials, and provider state untouched. A later session does not restore removed Endpoint selection merely because discovery sees the service again.

What crosses each boundary​

Connector-owned Connection + Connector Grant
                   ↓ value-free projection
Agent Endpoint + session Endpoint Grant + admitted operation descriptions
                   ↓ bounded invocation result
worker-visible result + attributable evidence

The worker never receives a Connector credential, credential address, Connection object, daemon URL, backend URL, provider route, OAuth exchange, or generic authenticated proxy. A future datasource may bind an admitted read to compact record projections; selecting an Endpoint does not manufacture a datasource.
