Connect services without giving secrets to the worker

Choose where an operation runs and where its credential remains. The harness receives one opaque Connection and the operations admitted for it—not a password, token, vault reference, or raw endpoint.

Product pre-v1Work controllable dev coreDefault bounded

The short version​

An engineer connects a service once. Connectors keeps the resulting authority at the place where provider operations run: on the engineer's machine, in a central deployment, or at a satellite near a private service. The coding worker sees the same Connection either way.

Two choices stay independent:

  • Execution placement decides which Connector reaches the service: personal-local, central, or satellite.
  • Credential source decides how that Connector authenticates: workload identity, its managed encrypted store, or an approved external provider such as 1Password.

The selected Integration policy fixes the compatible combinations. A task or model cannot switch placement, credential source, provider account, or destination.

Developer harness and web product​

The two experiences do not need to look alike:

Developer harnessHosted web product
Usual setup ownerthe developeran organization operator or signed-in end user
Usual Connectorpersonal-local, plus selected organization Connectionscentral or satellite
Usual credential sourceOS keychain or the developer's 1Passwordorganization workload identity, encrypted store, or secret provider
Usual connection flowprotected local prompt or local approvalhosted browser authorization or target-sealed remote entry

A browser product cannot silently use a developer's local keychain or 1Password session. That path requires a separately installed, deliberately paired personal Connector, and operations continue to run there. Likewise, a local harness does not inherit organization credentials merely because a remote Connector is reachable. It receives only the Connection and operations admitted to it.

This allows the setup journey to fit its user while preserving one Connection lifecycle, Grant model, operation catalog, and evidence contract.

Use an organization connection​

Choose this when your organization already operates a Connector beside the service. For a private Grafana deployment, the path can be:

harness → central Connectors → outward federation → cluster satellite
                                               → grafana.monitoring.svc.cluster.local

The satellite addresses a stable Kubernetes Service, not an individual pod. Ideally its workload identity is mapped to a read-only provider identity by an auth proxy or service mesh, so there is no reusable Grafana token to store. A tightly network-restricted anonymous Viewer can be useful during development, but an accountable workload identity is the preferred released posture.

If the provider still requires a bearer token, that token remains in the satellite's credential source. Central Connectors coordinates a signed operation; it does not receive the token.

Use a service discovered through another service​

Some providers list other configured services. For example, an admitted Grafana data-source read can observe Prometheus, Loki, or Alertmanager backends. The harness must not treat that vendor object as a ready Endpoint:

Grafana Connection + Grant → observation → candidate
                                      → explicit native Connection + its own Grant
                                      → opaque Agent Endpoint + Endpoint Grant

The child keeps its native semantics. A Prometheus child exposes reviewed Prometheus operations even when its fixed route travels through Grafana. It does not expose a generic Grafana proxy, and its Grant does not authorize Grafana operations. The native Provider identity names the API contract, not another login or credential. Parent and child share placement, the route is one mediated hop, and an unavailable adapter or stale observation degrades the child instead of falling back to direct network access.

Connectors retains the parent credential, Grafana data-source identifier, backend URL, resource binding, and proxy path. The harness receives only a safe label, native Provider identity, opaque Endpoint reference, lifecycle state, and operations admitted for the task. This makes a discovered service feel like any other datasource without collapsing discovery, connection, and consent.

Paste a credential securely​

The normal personal flow can be as simple as Add connection → Paste securely. A trusted local completion prompt hides the input and sends it once to the local Connector. The Connector stores the credential in the operating-system keychain.

It does not write a plaintext credential file, export an environment variable, add a command-line argument, or place the value in harness configuration. The one-use completion endpoint belongs to Connectors and is never shown to the coding worker. Completion returns only the durable Connection.

Use a credential provider​

A developer may instead connect 1Password or another approved secret provider, then select one credential for a second Connection. The selected value remains in the provider:

connect credential provider → approve item binding → create service Connection

harness → local Connector → constrained credential-provider binding → service

The credential provider can use the regular connection experience for human authorization, but its runtime role is deliberately narrower than a normal model-facing connector. Connectors holds an opaque binding and may resolve it only while executing an admitted provider operation. There is no general secret.read operation and the worker cannot see vault, item, or field locators.

Unlock and user-presence rules remain under the credential provider's control. A deployment may keep a short-lived provider session where policy permits; it must not copy the selected credential into ordinary configuration as a convenience cache.

Store at a remote Connector​

Sometimes the credential should live with a deployed satellite even though the engineer completes setup from elsewhere. The user journey remains Add connection → Paste securely, but the completion is sealed to the destination Connector before it leaves the trusted human-facing client:

human input → encrypt to one-use satellite key → central relays ciphertext
           → satellite consumes once → encrypted deployment credential store

The satellite still opens only its outward federation connection; this does not create an inbound management listener or reverse tunnel. Central can route the encrypted completion but cannot decrypt it. The satellite accepts it only for the intended tenant, Integration, placement, current policy generation, and unexpired Connect Session. There is no API for reading the stored value back—only value-free status, rotation, revocation, and deletion.

“Never read” means no user, harness, model, management client, response, log, audit entry, or database row can retrieve the value. The trusted Connector runtime must still resolve it briefly, after every authority check, to authenticate the declared provider request.

Sign in with the provider​

OAuth2 fits into the same model. The human authorizes in a browser; the Connector assigned to the Connection owns state and PKCE, exchanges the authorization result, stores or binds the resulting tokens at its execution placement, and refreshes them. The worker sees only completion status.

OAuth2 is an acquisition method, not another storage location. Browser sign-in to a provider does not automatically create a usable API credential; the Provider must declare a compatible delegated API flow for the selected placement. An incompatible flow is refused rather than silently moving token custody somewhere else.

Deployment policy chooses the storage backends​

The Connector deployment configuration declares which credential sources exist and where they are allowed: for example, a personal OS keychain, an organization credential provider, an encrypted satellite store, or workload identity for one cluster. It contains policy and opaque references, never credential values.

Even when a product exposes one common or global configuration file, this remains a Connector-owned section. The harness or web application may choose a permitted Connection; it does not configure a secret-store driver. Each Integration narrows the deployment list, and connection setup selects from that intersection. Invocation cannot change it.

If a configured source is unavailable, the Connection becomes degraded and asks for repair. It does not fall back to an environment variable, plaintext file, different vault, central store, or different placement. Changing a default also does not silently migrate existing credentials.

What the harness can see​

After any successful route, a session may receive:

  • a human label and opaque Connection reference;
  • whether the Connection is callable, degraded, or needs the engineer to reconnect;
  • a safe custody summary such as organization workload, local keychain, credential provider, or satellite store;
  • the operations currently admitted by both the Connector Grant and the task boundary;
  • bounded, redacted operation results and attributable evidence.

It cannot receive the credential value, credential address, provider locator, completion endpoint, OAuth exchange material, raw destination, or a generic authenticated proxy.

Current maturity

This page describes the target connection experience. A first personal-local development slice now proves Grafana discovery, explicit materialization, independent target Grants, and fixed mediated execution with a memory-only credential. Durable custody, broader deployment topology, and the general Agent Endpoint projection remain open. The harness does not yet ship a released general Connector binding. Check current status before relying on it.
