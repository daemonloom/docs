What Zwirn actually does

Zwirn runs one coding-worker session through an explicit workspace, operation surface, effect ceiling, and evidence boundary. The current development build exposes the same session through a terminal UI, local web workspace, or strict JSONL.

Product pre-v1Work controllable dev coreDefault bounded

What you can run today​

From an admitted source checkout, the current development build provides four entry points:

SurfaceCommandUse it for
Terminal UIzwirn --cwd /absolute/workspaceinteractive prompts, proposals, approvals, steering, cancellation, capability and evidence views
Local web workspacezwirn --cwd /absolute/workspace webthe same session in a loopback-only browser workspace
Server onlyzwirn --cwd /absolute/workspace serveprint the private bootstrap URL without launching a browser
Strict JSONLzwirn --cwd /absolute/workspace run --headlessmachine-controlled runs over versioned input/output frames

All four use the same session engine and capability compiler. The default route drives the pinned Codex app-server using Codex's own login; --inference-route fixture selects a deterministic, no-provider compatibility path. Neither route falls back to the other. This is pre-v1 development software, not a stable public distribution or hosted service.

The quickstart gives exact prerequisites, commands, expected states, and common refusals.

One run in four steps​

frame outcome → compile boundary → run and intervene → verify evidence
  1. Frame: name the outcome, exact workspace, exclusions, stop conditions, and completion evidence.
  2. Compile: intersect passive observations, owner facts, grants, and product policy. The result can only narrow authority.
  3. Run: let the worker call only admitted operations. Today that means the native workspace.status read plus explicitly selected Connector reads; general project file access, editing, tests, terminal, diff, and preview are not ordinary Zwirn capabilities yet. Steering changes the next step; approval handles one exact boundary delta; cancellation remains terminal.
  4. Verify: distinguish the worker's conclusion from workspace changes, test results, Connector audit, Substrate observations, and remaining uncertainty.

Prompt-led and proposal-led activity modes change who suggests the work, not what the run may do.

What the boundary contains​

PartConcrete meaning
Workspaceone explicit root; parent directories are not searched; the worker gets a bounded workspace.status operation, not the mounted project tree
Capability resourcesobserved repositories, CI systems, clusters, databases, or documents; observation alone grants nothing
Endpoint operationsexact Connector-backed operations surfaced for selected opaque Endpoints; invocation is rechecked by Connectors
Worker routean explicitly selected supported worker and inference route; failure never selects another route
Limits and effectsfinite run/cancellation bounds, network posture, and the highest effect admitted without a new decision
Completion evidencethe checks and owner observations required before the product or engineer accepts the result

Datasource is intentionally narrower than capability resource: it is reserved for a future named, read-only record surface with compact owner-declared projections. The current capability graph does not call every workspace, cluster, or operation set a datasource.

When the next step does not fit​

Suppose a task finds a likely cause and the worker asks to retry a release. No such operation exists in the current ordinary product surface, so approval cannot manufacture it. A future deployment that declares and admits the operation would still present one correlated decision; approval would permit only that attempt, and a separate observation would be required to say whether it worked.

Start with Run the harness locally. Use task recipes for copyable work packets, Connecting services for current Endpoint setup, and Current status for the implementation boundary.
