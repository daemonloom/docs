Read Zwirn decisions and evidence

Use the effective operation surface to see what may run, treat approval as permission rather than success, and require terminal evidence from the owner that can actually support each claim.

Product pre-v1Work controllable dev coreDefault bounded

Follow one implemented operation​

The built-in local example is deliberately small and executable:

workspace observed
  → owner reports availability/admission
  → workspace.status enters the effective capability surface
  → worker searches and describes the operation
  → invoke rechecks the exact profile and target
  → bounded result is attributed to the native operation provider
  → /surface workspace.status off removes it immediately
  → /surface workspace.status on proposes one exact restoration

The worker has no mounted project tree and cannot replace the absent operation with shell, raw filesystem, HTTP, or another provider. Approval can restore only the operation already present in the immutable ceiling; it cannot create a new tool or permission.

Interpret states literally​

Event or factWhat it provesWhat it does not proveOperator action
Resource observedone bounded observation existsowner availability, access, or an operationinspect owner facts and the effective surface
Operation describedcurrent schema/effect/target is visibleinvocation is reserved or will still be admitted laterinvoke only through the supervisor
Approval acceptedone correlated action/profile delta may proceedthe effect succeeded or future actions are allowedwait for completion and owner evidence
Cancellation requestedthe stop request was recordedthe worker/process/effect is terminalwait for terminal reconciliation
Response lost after mutationthe request may have crossed the effect boundaryfailure, success, or safe retryinspect provider state/idempotency first
Operation absentthe current run cannot call itthe provider never supports itinspect profile/Grant; do not improvise a fallback

Unknown or missing facts remain unknown or missing. They never become zero usage, an empty result, a default Grant, or success.

Read the Endpoint path​

Connector-backed operations have two independent authority checks:

Connector observation → candidate → materialized Connection + Connector Grant
                                             ↓ value-free Agent projection
                              Endpoint + session Endpoint Grant
                                             ↓
                              endpoint-targeted operation surfaced
                                             ↓ invoke
                              Connector rechecks Connection + Grant

The worker sees an opaque target and bounded descriptions/results, not the Connection, Grant, credential, backend URL, or proxy route. Revocation removes the Endpoint's operations on recompile; rediscovery cannot reinterpret a higher-generation tombstone as renewed consent.

Ask which owner observed each claim​

OwnerWhat its evidence can supportWhat it cannot decide alone
Product/engineerobjective, policy decision, and whether evidence satisfies the taskprovider effect or process termination
Agentrun ordering, controls, profile generation, and terminal lifecycleprovider-facing effect or OS confinement
Coding workernative session activity and its conclusionits own authority, independent success, or hidden process state
Connectorsadmitted external request, redaction, provider response, and auditproject workspace state or task acceptance
Substrateprocess tree, runtime profile, workspace mount, resources, and terminationmodel/provider truth or external business outcome

Those facts may agree, contradict one another, or remain incomplete. There is deliberately no single “safe” or “successful” switch that erases those distinctions.

Keep credentials out of the proof​

Codex owns its own login; Agent passes the selected Codex home to the harness but never reads its cached auth. Connectors owns external-system credentials and resolves them only after its own authorization checks. Neither class of secret belongs in the task, prompt, generic environment, transcript, fixture, result, or evidence packet.

When an operation is unavailable, repair its owner boundary. Never paste a token into the prompt, export it as a convenience environment variable, switch to raw HTTP, or treat a vault address as a safe substitute for the secret. See Connecting services.

Recover without rewriting history​

A completed, failed, or cancelled run is terminal. A cancellation request waits for terminal acknowledgement. An external provider may have accepted an effect just before a response was lost; a worker process may have stopped while a descendant remains unproven. In either case, the correct state is outcome unknown until the owning boundary reconciles it.

Recovery creates new attributable work: inspect provider state, compensate, retry under a declared idempotency rule, restore a checkpoint, or begin a replacement task. It never edits the earlier attempt until it appears successful.

Seven checks before admission​

Before admitting work, ask:

  1. Is the outcome precise enough to know when to stop?
  2. Which detected sources are actually admitted, and why?
  3. Which effects can occur without another decision?
  4. Where do credentials and model authentication remain?
  5. What happens if the worker, Connector, or execution boundary fails?
  6. Which independent observations are required for completion?
  7. Can the result be inspected, handed off, or reversed without trusting the transcript alone?
