A four-step exercise​

  1. Keep Investigate a release, Read only, External operations: Read, and Network: Named route. Expect workspace.inspect and ci.read; release.retry stays excluded.
  2. Change External operations to Gated change. The exact retry becomes approval-required—it does not run.
  3. Change Network to None. Both ci.read and release.retry disappear because no named provider route remains.
  4. Restore the named route, advance to PROPOSE, choose approve/deny/steer, then inspect the final text. Even approval is recorded separately from an observed outcome.

What the model teaches​

The list is an effective capability surface, not a list of everything installed or detectable. In the active design, an operation reaches that list only when its operation provider, explicit resource-or-Endpoint target, boundary, Endpoint Grant where applicable, owner snapshot/facts, operation identity, and effect all match the immutable profile.

A Connector-backed operation targets a surfaced Endpoint and needs an active Endpoint Grant plus a current owner snapshot. Connectors independently rechecks its Connection and Connector Grant on invocation. Revocation is monotonic, so recompilation removes the Endpoint's operations and rediscovery cannot silently reactivate it.

What is real versus simulated​

The four recipes answer “what kind of work is this?” They do not grant access. The current product does implement prompt-led and proposal-led built-in Workflow execution, the native workspace.status operation, exact profile narrowing/restoration, Endpoint projection, and session controls.

The simulator's general file reads/writes, checks, remote changes, and five task recipes are product direction. A future installed Work Mode binds those surfaces to an exact Workflow, worker route, capability ceiling, approval posture, limits, evaluation, and evidence requirements. Initiative never expands authority in either the implemented or simulated path.
